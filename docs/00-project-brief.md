# 企业知识问答 Agent：开发总纲

> 状态：规划基线  
> 选题：企业知识问答 Agent  
> 目标：统一我们对需求、验收标准、技术边界和提交材料的理解，后续代码与测试均以本文为准。

## 1. 项目定位

本项目面向需要查询企业制度、FAQ 和产品规则的员工。系统必须基于给定资料回答，清楚展示答案依据；资料不足、资料冲突或工具不可用时，应给出可解释的任务状态，不能猜测。

核心价值是可靠性，而不是闲聊能力。检索命中不等于答案正确，引用存在也不等于引用支持结论。每条实质性结论都必须能追溯到明确的文档 ID、版本日期和原文片段。

目标交付为本地单机 Web 工作台：命令行一键启动后，可上传资料、构建知识库、检查文档分块与检索日志，并通过会话提问。保留 CLI 作为离线评测和诊断入口；默认提供离线 Mock，也支持配置真实模型。业务工具使用本地函数，不做云部署、多用户或生产级分布式运行时。

## 2. 用户、目标与范围

### 2.1 目标用户

- 需要快速查询报销、休假、考勤或产品规则的一线员工。
- 需要核对制度版本和适用范围的 HR、行政或产品人员。
- 需要验证 Agent 行为是否可靠的评审者。

### 2.2 必须解决的问题

- 将自然语言问题、可选对话历史转换为可检索的查询。
- 根据检索摘要决定读取原文、补充检索、追问或结束。
- 用文档 ID、版本日期和原文片段支撑答案。
- 识别不同文档之间互相冲突的规则，并请求用户补充适用范围。
- 识别资料库没有覆盖的问题，报告资料缺口。
- 工具失败时停止依赖失败结果，说明影响并返回明确状态。
- 利用对话上下文理解“那它”“这个流程”等追问。
- 在改写、近义词和同义表达下仍能检索到正确资料。

### 2.3 暂不纳入范围

- 登录、权限管理和真实企业数据接入。
- 云端部署、生产级可观测性平台。
- 多 Agent 编排和复杂工作流框架。
- 自动修改或发布企业制度。
- 未经证据支持的开放式建议。

## 3. 输入、输出与状态契约

### 3.1 输入

```json
{
  "question": "报销期限是多久？",
  "history": [
    {"role": "user", "content": "我在上海办公。"},
    {"role": "assistant", "content": "已记录办公地点。"}
  ]
}
```

`question` 必填，`history` 可选。输入进入 Agent 后应保留稳定会话 ID，便于在上下文中解析指代。

### 3.2 统一输出

```json
{
  "answer": "D01 规定报销期限为 30 天；D02 规定为 15 天。",
  "citations": [
    {
      "document_id": "D01",
      "version_date": "2026-01-01",
      "quote": "员工应在费用发生后 30 天内提交报销。"
    },
    {
      "document_id": "D02",
      "version_date": "2026-05-01",
      "quote": "员工应在费用发生后 15 天内提交报销。"
    }
  ],
  "gaps": ["两份文档均未说明各自适用范围或优先级。"],
  "status": "needs_clarification",
  "question_to_user": "请确认本问题适用中国大陆普通员工制度，还是上海地区制度。"
}
```

`citations` 中的 `quote` 必须逐字来自资料。`answer` 只能陈述引文能够直接支持的事实。`gaps` 记录缺失前提、冲突或未能检索到的信息。

建议固定以下状态：

| 状态 | 含义 |
|---|---|
| `completed` | 已由一致证据支持并完成回答 |
| `needs_clarification` | 证据冲突或缺少必要前提，需要用户确认 |
| `not_found` | 当前资料库不足以回答问题 |
| `tool_error` | 关键工具失败，无法可靠完成 |
| `step_limit` | 达到步数或工具调用上限，任务未完成 |

不得用自由文本替代任务状态。达到执行上限时必须返回 `step_limit`，并在 `gaps` 中说明停在哪里。

## 4. 资料与数据要求

每条文档至少包含：

```json
{
  "document_id": "D01",
  "title": "中国大陆员工报销制度",
  "version_date": "2026-01-01",
  "scope": "中国大陆普通员工",
  "content": "员工应在费用发生后 30 天内提交报销。"
}
```

合成资料应覆盖以下组合：

- 一个可直接回答的普通制度问题。
- 两个文档对同一指标给出不同数值，但没有适用范围或优先级。
- 一个可通过适用范围消除的冲突案例。
- 一个只有较低版本被检索引擎优先召回、需要读取原文或补充检索的案例。
- 一个 FAQ 与正式制度的近义问法，用于验证改写和相似问题。
- 一个资料库完全没有覆盖的问题。
- 一个工具超时、异常或返回空结果的案例。

所有资料必须标记为合成数据，不使用真实员工、客户、密钥或内部制度原文。

## 5. 工具设计

建议提供两个核心业务工具，并让模型看到清晰的参数和返回值：

### 5.1 `search_documents`

输入：

```json
{"query": "报销提交期限", "top_k": 5}
```

返回文档 ID、标题、版本日期、范围、摘要和分数。摘要用于选择下一步，不能直接作为最终引文。

### 5.2 `read_document`

输入：

```json
{"document_id": "D01", "query": "报销期限"}
```

返回完整原文或相关片段、版本日期和范围。最终引用必须来自这里，而不是检索摘要。

真实场景可增加 `list_versions` 或 `search_by_scope`，但核心验收阶段保持工具面简洁，便于证明动态决策。

所有工具应支持注入可控故障，用于测试超时、异常和空结果。工具参数与返回摘要必须写入 Trace。

## 6. 动态决策循环

至少实现一个真实的“模型选择动作 -> 执行工具 -> 观察结果 -> 调整下一步或结束”循环。固定分支、自动重试和预先写好的日志不能替代模型决策。

推荐提示模型从以下动作中选择：

- `search_documents`：初始问题含混、召回不足或别名很多。
- `read_document`：摘要命中但不足以确认条款、范围或版本。
- `search_documents` 再次调用：第一次召回无结果、结果偏题或发现新实体和关键词。
- `ask_user`：文档冲突且缺少适用前提，或问题本身缺少决定答案的信息。
- `finish`：证据一致且引用充分。

每次工具调用后记录：

- 当前步骤序号。
- 模型选择的动作及工具参数。
- 工具返回摘要。
- 下一步动作和简短决策依据。
- 累计工具调用次数。

Trace 只记录可审计决策摘要，不记录或伪造模型内部思维过程。

建议默认上限为 6 个 Agent 步骤或 4 次工具调用，取先到者。上限应在运行时配置，并通过测试验证。

## 7. 冲突处理规则

### 7.1 安全规则

如果多个文档对同一问题给出不一致事实，且资料未提供适用范围、优先级或明确废止关系：

1. 列出所有冲突文档及原文。
2. 明确说明资料未给出适用条件或优先级。
3. 返回 `needs_clarification`。
4. 提出一个能消除歧义的具体追问。

不得自行选择较新版本、较严格数值、出现频率更高的答案或“通常更合理”的答案。

### 7.2 参考案例

问题为“报销期限多久”：

- `D01` 写明“报销期限 30 天”。
- `D02` 写明“15 天”。
- 两份材料均未给出适用范围与优先级。

正确行为：列出 D01 和 D02 的原文，报告冲突与资料缺口，请求用户确认适用制度，状态为 `needs_clarification`。

如果只检索到 D01 且没有其他冲突证据，可以依据 D01 回答。若 D02 存在于资料库但第一次未被召回，Agent 应通过补充检索或读取相关原文发现潜在冲突，不能以“第一次没搜到”为充分理由直接回答。

### 7.3 可消除的冲突

如果文档或用户历史明确给出适用范围，例如用户补充“我是中国大陆普通员工”，且 `D01` 的范围匹配、`D02` 的范围不匹配，则可选择 `D01`，但回答仍应引用范围条款和期限条款。

## 8. 上下文追问

设计至少一组多轮案例：

1. 用户询问“上海办公室的报销期限是多久？”
2. Agent 基于上海制度回答。
3. 用户追问“那国外出差呢？”

第二步应利用历史中的“报销期限”实体，将省略问题改写为“国外出差报销期限”。回答时仍要重新检索并引用资料，不能只复述上一轮引用。

上下文只用于补全意图和指代。每次事实回答必须由当前资料验证。

## 9. 检索改进策略

离线入口可以使用轻量的同义词与关键词扩展，真实模型入口由模型进行查询改写。建议至少覆盖：

- 报销几天内交、费用提交时限、报销截止日期等近义表达。
- 文档 ID、标题、正文和范围字段。
- 最新版本优先作为排序信号，但不能据此静默消除同等有效资料的冲突。
- 对首次结果不足、结果冲突、只出现摘要字段的情况触发第二次检索或原文读取。

检索模块应保留可复现结果。若使用向量检索，应固定数据、模型和参数，并在离线环境下提供降级方案。

## 10. 技术取舍

采用 Python 本地 Web 应用作为主入口，并保留 CLI 离线评测入口。Agent 编排优先使用 LangGraph 与 LangChain，重点保证：

- 输入、输出和 Trace 均为结构化 JSON。
- 工具与模型客户端可替换，支持真实模型和离线 Mock。
- 决策循环、步数限制、冲突检测可以单元测试。
- 运行命令可复制，不依赖线上服务才能验收。

首版使用 LangGraph StateGraph/ToolNode 管理动作循环，使用 LangChain tools 与 ChatModel 抽象连接工具和模型；不自行重写通用 Agent runtime。框架使用本身不构成评分证据，仍须验证模型是否根据工具观察动态调整动作。

真实模型接入应通过环境变量配置，不提交密钥。离线 Mock 只验证控制流、工具协议和输出契约，不宣称证明真实模型决策效果。

## 11. 必须验收的场景

| 验收点 | 场景 | 期望行为 |
|---|---|---|
| 明确答案 | 单一制度明确回答期限 | 返回 `completed`、准确答案、文档 ID、版本与原文 |
| 文档冲突 | D01 为 30 天、D02 为 15 天且无范围 | 返回两份证据、冲突缺口、追问和 `needs_clarification` |
| 资料外问题 | 询问资料库没有的主题 | 明确不提供猜测，报告检索过的资料缺口，返回 `not_found` |
| 改写相似问题 | “报销要几天内交” | 检索到与“报销期限”相同的正确文档 |
| 上下文追问 | “那国外出差呢？” | 从历史补全“报销期限”，重新检索并引用 |
| 工具失败 | 检索或读取工具抛错/超时 | 说明故障影响，返回 `tool_error`，不能伪造答案 |
| 执行上限 | 模型持续检索仍无法收敛 | 返回 `step_limit` 和未完成原因 |
| 动态决策 | 两个不同工具结果导致不同下一步 | Trace 展示至少两条不同执行路径 |
| 引用忠实性 | 替换资料中的数值或范围 | 回答和决策随资料更新而改变，不依赖硬编码 |

## 12. 测试与评估

测试分为两层：

1. 确定性单元/集成测试：检索、原文读取、冲突检测、状态、步数限制、工具异常、输出 schema。
2. 模型行为回归：固定模型和提示词，运行真实模型案例；离线 Mock 案例单独标注。

至少提交三组完整的输入、实际输出与 Trace：

- 正常路径：明确答案，可能包含补充检索或原文读取。
- 信息不足路径：冲突、资料外问题或多轮上下文追问。
- 工具失败路径：返回 `tool_error`，记录失败工具与恢复决策。

同一案例可以覆盖多个验收点。评估文档必须引用对应 Trace 文件，并把预期、实际、失败原因和限制放在一起。

引用忠实性测试应直接替换合成资料中的关键内容，例如把 `30 天` 改为 `45 天`，验证答案、引用和动作随之改变。

## 14. 三小时执行优先级

### P0：完成可验收核心链路

- 结构化文档数据和两个工具。
- 真实模型驱动的决策循环。
- 步数与工具调用上限。
- 明确答案、冲突、资料外、上下文追问、工具失败五类测试。
- 至少两组不同执行路径的真实 Trace。
- README 运行命令和离线 Mock 入口。

### P1：提高检索与冲突可靠性

- 相似问法改写。
- 第一次检索不足后补充检索。
- 版本、范围与原文读取。
- 引用忠实性替换测试。

### P2：工程完善

- 更细的日志。
- 可选的 HTTP API。
- 更多文档与中文分词方案。
- 生产级重试、缓存和可观测性。

时间不足时优先保留 P0 与能形成证据的 P1，明确记录未完成部分和实际用时。

## 16. 主要风险与检查点

- 只记录固定分支：应证明模型在不同观察结果下选择了不同动作。
- 引用摘要冒充原文：最终引用必须来自文档原文读取结果。
- 冲突时静默选新或选严：无范围与优先级时必须追问。
- Mock 结果被当成真实模型能力：文档中分别列明离线验证与真实模型验证。
- Trace 泄露内部思维：只保留动作、参数、观察摘要、后续动作和简短理由。
- 案例只覆盖 happy path：把工具失败和步数上限纳入自动测试。
- 结果不可复现：固定资料、模型参数、依赖版本和运行命令。

## 17. 当前环境故障排查记录

本次开发曾遇到 Codex 会话未提供终端或文件工具。排查结果如下：

- 当前 CC Switch 版本为 `4.0.24`，已是当时最新版。
- 当前模型目录声明了 `shell_type: unified_exec`、`supports_search_tool: true` 和 `apply_patch_tool_type: freeform`。
- 新会话已实际提供终端和文件工具，能够执行 `git`、读取文本并写入仓库。
- 旧会话可能保留启动时形成的工具快照；切换模型后应完整重启 Codex 并新开会话。
- PATH 中的 `codex` 为 `0.142.0`，桌面会话捆绑运行时为 `0.166.0-alpha.5.1`。后续提交前应确认实际使用的是哪个运行时，避免旧 CLI 与桌面版混用。

CC Switch 的公开 issue 表明，旧版本中存在三类相关原因：切换供应商重写模型目录、第三方模型工具声明不完整，以及本地协议转换遗漏 `tool_search` 或延迟加载工具。新版已经修复这些路径；若再次出现，应先完整退出桌面端、确认当前供应商和模型、重新切换并新开会话，然后收集版本、供应商、模型与脱敏日志。
